A/B testing prompts

How to tell whether a new prompt is really better, or just got lucky on this run.

The one rule Change one thing. Hold everything else fixed. Use the same inputs. Ship only if the gap beats the noise.
model snapshottemperaturetoolscontext / RAGgolden setgrader

Only the prompt differs: A = current vs B = challenger

The three stages

Most prompt A/B testing is the offline stage. You go online only when the prompt affects a business metric.

Stage 1 · Offline

Eval on a golden set

  • 100–1000 real, labelled cases
  • 3–5 runs per case
  • Paired stats + read the diffs
Stage 2 · Shadow / canary

Real traffic, low risk

  • Shadow: B runs, users still see A
  • Canary: B serves 1–5%
  • Watch latency, cost, errors
Stage 3 · Online A/B

50/50 split by user

  • Feature flag assigns variant
  • 1 primary metric + guardrails
  • Fix duration up front; no peeking

Grade cheapest-first

GraderUse forCost
Code checksExact label, regex, JSON schema, "contains order ID"Free, deterministic
LLM-as-judge + rubricTone, helpfulness, faithfulness to the sourceCheap, biased (see below)
HumansFinal call on subjective tasks; calibrating the judgeSlow, expensive

LLM judges have three known biases

PositionPrefers whichever answer is shown first.Fix: run both orders, keep only consistent verdicts.
VerbosityPrefers longer answers even when worse.Fix: rubric scoring, not "which is better?"
Self-preferencePrefers outputs from its own model family.Fix: judge with a different model; check against 50–100 human labels.

DoWhy
Randomise by user, not requestOne person shouldn't see both prompts
One primary metric (task success, thumbs-up, conversion)5 metrics at α = 0.05 → ~23% chance of a false win
Guardrails: p95 latency, cost/request, error & refusal rateB can win quality and still be unshippable
Fix sample size and duration up frontStopping when it "looks good" inflates false positives

Mistakes that give away a beginner

  • Eyeballing 10–20 hand-picked examples
  • Changing the prompt and the model at the same time
  • One run per case at temperature > 0
  • Tuning and evaluating on the same examples
  • Reporting only the average and hiding the slice where B got worse
  • Trusting an LLM judge you never checked against humans

Your interview answer

"I treated prompts like code: versioned in git and evaluated against a golden set of real cases. For each change I ran an offline A/B with the model and temperature pinned and 3 samples per case. Grading used deterministic checks plus a rubric-based LLM judge that I calibrated against human labels. I compared variants with a paired bootstrap CI and only promoted a prompt if it beat the baseline outside the noise without regressing cost or latency. Winners went to a canary behind a feature flag."

Expect these follow-ups
How big was the eval set? · How did you know the judge was right? · What effect size could you detect? · What happened when B won on average but lost on a slice?
